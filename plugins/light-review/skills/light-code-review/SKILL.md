# light-code-review

**説明ファースト**の軽量 PR レビュー skill。finding のリストを吐くゲート（`isolated-code-review`＝フル）とは役割が別物。

## これは何のためか（設計の芯）

素の finding リストは「問題」しか言わず、読む人に前提が無い。人も LLM も「そもそもこのコードは何？作者は何をしたかった？あるべき姿は？」を毎回再構築させられ、その**再構築コストが本当の負担**になる。

この skill は前提を **PR の意図から滝で下ろす**ことでその負担を消す:

> このPRは何のため → 指摘箇所はその中の**どの部分**か → 実装者は**どういう意図**で → **でも実際はこうなってて** → あるべき姿との**乖離** → 放置の**影響**

この連なった状態で読ませるのがゴール。だから **「軽い」＝読む人の認知負荷が軽い**であって、計算量や観点数を減らすことではない。

## 原則

- **PR の意図が全ての前提の頂点。** ここを取り込まずに個別の指摘を書かない。
- **コードスメル中心。指示は薄く、モデルの性能に任せる。** 網羅的なチェックリストは課さない。「気になるコードの匂い」を拾う。
- **OK だった箇所も理由付きで明示する。** 承認の根拠を残すことが人の学びになる（これがフルとの決定的な違い）。
- **前提を省略しない。** その箇所だけ読んだ人が何が問題か分かる状態にする。
- read-only。コードは変更しない。まずは **レビュー文を生成するだけ**（自動投稿はしない）。

## 前提

- `gh` CLI が使えること（PR を対象にする場合）。`gh auth status` で確認。
- TAKT は不要。この skill は親セッションでそのまま動く。

## 手順

### 1. 対象を特定する（一問ずつ）
候補を一つずつ確認して確定する:
- PR 番号（`#42`）または PR URL
- working tree の未コミット変更（`git diff`）／ブランチ差分（`git diff <base>...<branch>`）

### 2. PR の意図を取り込む（前提の頂点）
対象が PR なら、まず意図を吸う:
```bash
gh pr view <n> --json title,body,headRefName,baseRefName,commits,closingIssuesReferences
gh pr diff <n>
```
- タイトル・本文・リンク issue・コミットメッセージから「**何のための PR か**」を一段落で言語化する。
- working tree 対象なら、ブランチ名・コミット・（あれば）issue から同様に意図を組み立てる。意図が読み取れなければユーザーに一言で聞く。

この「PR意図」が以降すべての説明の頂点になる。

### 3. コードスメルで対象箇所を拾う（薄い指示・モデル依存）
差分を読み、**気になる匂いのする箇所**と、**見たうえで問題なかった箇所**を拾う。
- 網羅チェックはしない。責務の混在・不自然な分岐・名前と実装の乖離・暗黙の前提・こぼれる例外経路・過不足なデータ・重複や早すぎる抽象 …といった「匂い」をモデルの判断で拾う。
- 拾った各箇所を、必ず **PR意図の中での位置づけ**に紐づける（頂点から辿れる状態にする）。

### 4. 各箇所を説明フォーマットで展開する
気になる箇所は以下を**前提を省かず**埋める:
- **機能**: その箇所が何をするコードか、システム全体の中でどの機能のあたりか（自然言語・前提知識の共有）
- **実装者の意図（推測）**: PR意図から辿った、作者がやりたかったこと。推測と明示する。
- **現状**: でも実際はこうなっている。
- **あるべき姿との乖離**: 理想の形と、実装とのギャップ。
- **放置した場合の影響**: 具体的に何が起きるか（曖昧語で濁さない）。

OK だった箇所は「機能」＋「なぜ OK と判断したか（承認の根拠）」を簡潔に。

### 5. PR draft 用に出力する
下記フォーマットで、そのまま PR に下書きとして貼れる Markdown を返す:

```markdown
## ライトレビュー — <PR タイトル>（#<n>）

### このPRは何のためか
<PR意図の一段落要約。何を達成しようとしているか>

### 確認して問題なかった箇所
- **<file:line ／ 機能名>** — <機能説明（システム内の立ち位置）>。<OKと判断した理由＝承認の根拠>

### 気になる箇所
#### 1. <file:line ／ 機能名>
- **機能**: <自然言語の機能説明。PR意図の中でのこの箇所の位置づけ>
- **実装者の意図（推測）**: <…>
- **現状**: <でも実際はこうなっている>
- **あるべき姿との乖離**: <理想と実装のギャップ>
- **放置した場合の影響**: <具体的に>
```

- 気になる箇所が無ければ「気になる箇所」節は「特になし」とし、確認した箇所とその OK 理由を厚く書く。
- 出力後、「この文面を PR に下書きコメントとして投稿しますか？」と一度だけ確認し、望まれたときだけ `gh pr comment <n> --body-file <file>` 等で投稿する（既定は生成のみ）。

## scope 外

- コードの自動修正・commit・push。
- 承認/マージ、CI 組込。
- 網羅的な観点別ゲートレビュー（それは `isolated-code-review`＝フルを使う）。
