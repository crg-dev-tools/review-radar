# light-code-review

**説明ファースト**の軽量 PR レビュー skill。finding のリストを吐くゲート（`isolated-code-review`＝フル）とは役割が別物。

## これは何のためか（設計の芯）

素の finding リストは「問題」しか言わず、読む人に前提が無い。人も LLM も「そもそもこのコードは何？作者は何をしたかった？あるべき姿は？」を毎回再構築させられ、その**再構築コストが本当の負担**になる。

この skill が削るのは指摘の数でも精度でもなく、**1 指摘を理解するのに必要な読解量**である。

- **前提は PR の意図から滝で下ろす**（設計思想はそのまま維持する）
- ただし**指摘の書式は逆ピラミッド**。結論を冒頭に置き、前提は結論を支える最小限だけ後置する
- 6 項目のフル展開は「確認して問題なかった箇所」にだけ使う（**書式を指摘と OK で非対称にする**）

「軽い」＝**読む人の認知負荷が軽い**であって、計算量や観点数を減らすことではない。

## 原則

- **「簡単にいうと —— ○○」の 1 文が書けない指摘は出さない。** それはまだ理解できていない指摘である。
- **PR の意図が全ての前提の頂点。** ここを取り込まずに個別の指摘を書かない。
- **重要度を左右する前提は、読み手に調べさせず指摘の中に書く。**（後述の前提テーブル）
- **未検証の主張を検証済みと同じ口調で書かない。**（検証状態ラベル）
- **スコープはこの PR が追加した行に限定する。** diff に見えている ≠ この PR の責任範囲。
- **コードスメル中心。指示は薄く、モデルの性能に任せる。** 網羅的なチェックリストは課さない。
- **OK だった箇所も理由付きで明示する。** 承認の根拠を残すことが人の学びになる（これがフルとの決定的な違い）。
- read-only。コードは変更しない。**verdict は出さない**（draft を置くまでで止まる）。

## 前提

- `gh` CLI が使えること。`gh auth status` で確認。
- TAKT は不要。この skill は親セッションでそのまま動く。

## 手順

### 1. 対象を特定する（一問ずつ）
候補を一つずつ確認して確定する:
- PR 番号（`#42`）または PR URL
- working tree の未コミット変更（`git diff`）／ブランチ差分（`git diff <base>...<branch>`）

### 2. PR の意図を取り込む（前提の頂点）
```bash
gh pr view <n> --json title,body,headRefName,baseRefName,commits,closingIssuesReferences
gh pr diff <n>
```
- タイトル・本文・リンク issue・コミットメッセージから「**何のための PR か**」を一段落で言語化する。
- working tree 対象なら、ブランチ名・コミット・（あれば）issue から同様に意図を組み立てる。読み取れなければユーザーに一言で聞く。

### 3. スコープを確定する（この PR が追加した行だけ）
base ブランチが追いついていないと、他 PR の変更が diff に見える。**それを件数にも severity にも含めない。**

```bash
gh pr view <n> --json commits --jq '.commits[].oid'   # この PR のコミット集合
git log --format=%H -1 <sha> -- <path>                # その行を入れたコミットの特定
git show <sha> -- <path>                              # コミット単位で追加行を確認
```

- 既存の設計ギャップを挙げる場合は「**本 PR が作った問題ではない**」と明記して分けて書く。
- 「同種が N 箇所」と数えるときは、N のうちいくつが本 PR かを必ず区別する。

### 4. プロジェクト規約を先に読む
指摘の根拠にも、**指摘を取り下げる根拠にも**なる。

- `.claude/rules/`（`code-change-scope.md` / `review-standards.md` / `openapi-as-sot` / `docs-sync-policy` / `parameter-store-policy` 等）
- `AGENTS.md` / `CLAUDE.md` の最小変更原則

特に**抽象化・共通化を要求する前に発動条件（対象件数の閾値・別チーム・別 deploy pipeline 等）を確認する**。閾値未満で共通化を求めると、指摘する側が規約違反になる。

### 5. コードスメルで対象箇所を拾う（薄い指示・モデル依存）
差分を読み、**気になる匂いのする箇所**と、**見たうえで問題なかった箇所**を拾う。
- 網羅チェックはしない。責務の混在・不自然な分岐・名前と実装の乖離・暗黙の前提・こぼれる例外経路・過不足なデータ・重複や早すぎる抽象 …といった「匂い」をモデルの判断で拾う。
- 拾った各箇所を、必ず **PR意図の中での位置づけ**に紐づける。
- **1 件の違反を見つけたら同類を全件 grep する**（数える範囲は本 PR の行）。

### 6. 重要度を左右する前提を調べて埋め込む
指摘を書く**前**に、その指摘の重要度に効くものだけ確定させる。読み手に調べさせない。

| 前提 | なぜ効くか | 調べ方 |
|---|---|---|
| **到達経路**（公開／認証済み／内部のみ） | 情報露出・入力検証系の severity を一桁変える | Terraform の `authorization` / `api_key_required` / WAF / IPSet。Origin 検証は CSRF 対策で**認証ではない**（curl で偽装可） |
| **消費者**（ブラウザ fetch／サーバ間／画面遷移） | CORS・エラー body の可読性の意味が消える | 呼び出し側を grep。repo 内に無ければ「外部・未確認」と書く |
| **監視の有無**（アラームが実在するか） | 「気づけない」の重み | **モジュールインスタンス数を数える**。呼び出し側のコメントの記述を信じない |
| **入口のバリデーション** | 素通し系指摘が成立するか | zod／スキーマの実体 |
| **上限値・リソース設定** | 資源枯渇系の成立条件 | `memory_size` / `timeout` / `batch_size` / 件数上限 |

「回帰である」と言う前は**変更前の挙動を確定させる**（例: Lambda proxy 統合で関数が throw したとき API Gateway が返すのは 502。`gateway_response` 未設定なら 4xx/5xx に CORS ヘッダは付かない —— こうした前提は毎回確認する）。

### 7. 検証状態を 3 分類してラベルを付ける
主張ごとに区別する。混ぜない。

- **実測／コード確認済み**: ファイルと行を示す
- **仕様・契約に基づく判断**: 「◯◯ の公開契約に基づく。実物は未確認」と明示し、**確定方法を 1 行添える**（測る／読む）
- **推測**: 「推測」と書く。または出さない

未検証がある指摘には `**要確認**:` 節を必ず置く。無い指摘では節ごと省略する。

### 8. 指摘を逆ピラミッドで書く（構造は固定）

```markdown
#### <file:line ／ 機能名>

簡単にいうと —— **<核心を 1 文。ここだけ読んで伝わる形>**

<核心を成立させる最小の根拠。3〜5 文。コード参照は file:line で>

**前提**: <重要度に効く前提。到達経路・消費者・監視の有無など>

**直し方**: <差分レベルのコード。数行で足りるなら実物を貼る>

**影響**: <具体的な数値・条件つきで 1〜2 文＋マージを止めるか>

**要確認**: <未検証の前提があればここに。無ければ節ごと省略>
```

守ること:
- 「機能／実装者の意図（推測）／現状／あるべき姿との乖離／放置した場合の影響」の**見出しを立てない**
- 意図の推測は、必要なら根拠の中に 1 文で溶かす（「◯◯したかったのだと読める」）。見出しを立てると必ず長くなる
- **severity は「マージを止めるか」の一軸で言い切る。** ラベルだけ置くのは禁止
  - 例: 「MEDIUM。マージブロッカーにはせず『直しておく』で十分」

### 9. OK 箇所は 6 項目フル展開でよい
OK 箇所は長くても読み手のコストにならない（読み飛ばしても損しない・承認の根拠として後から参照される）。ここでは前提を厚く書く:

- **機能**: その箇所が何をするコードか、システム全体の中でどの機能のあたりか
- **実装者の意図（推測）**: PR意図から辿った、作者がやりたかったこと
- **現状 / あるべき姿との一致**: なぜ OK と判断したか（承認の根拠）

### 10. 出力する

```markdown
## ライトレビュー — <PR タイトル>（#<n>）

### このPRは何のためか
<PR意図の一段落要約>

### スコープ
<本 PR が追加した行の範囲。diff に見えているが対象外のものがあれば明記>

### 確認して問題なかった箇所
- **<file:line ／ 機能名>** — <機能説明（システム内の立ち位置）>。<実装者の意図（推測）>。<OKと判断した理由＝承認の根拠>

### 気になる箇所
<逆ピラミッド（手順 8）を必要な数だけ>

### 本 PR が作った問題ではないが気になるもの
<既存の設計ギャップ。severity には含めない>
```

気になる箇所が無ければ「特になし」とし、確認した箇所とその OK 理由を厚く書く。

### 11. PR に pending（draft）review として置く

**MCP GitHub（`mcp__claude_ai_GitHub__*`）は private repo で 404 になる。`gh api` を使う。**

1. **patch を落として addressable 行を先に確定する**（先に anchor を決めると失敗する）
   ```bash
   gh api /repos/{owner}/{repo}/pulls/<n> -H 'Accept: application/vnd.github.v3.patch' > pr.patch
   ```
   hunk を走査して、コメント可能な**新ファイル行番号の集合**を作る。コメント可能なのは **hunk 内の追加行と文脈行のみ**。
2. アンカーできない行への指摘は、**最も近い addressable 行に置き、「対象は直下の◯◯」と冒頭に書く**。
3. **1 回の `--input <json>` で本文とインラインを同時に置く。`event` を付けなければ PENDING になる。**
   ```bash
   gh api -X POST /repos/{owner}/{repo}/pulls/<n>/reviews --input review.json
   ```
   ```json
   {
     "body": "## ライトレビュー — ...",
     "comments": [
       { "path": "backend/src/handler.ts", "line": 91, "side": "RIGHT", "body": "簡単にいうと —— ..." }
     ]
   }
   ```
   範囲外の行を 1 つ指定すると `422 Line could not be resolved` で**リクエスト全体が失敗する**。
4. **submit はしない。** verdict（APPROVE / REQUEST_CHANGES / COMMENT）は人間が決める。この skill は「下書きを置く」までで止まる。

投稿は既定では行わず、出力後に「pending review として置きますか？」と一度だけ確認する。

## 例（同じ指摘・before / after）

**before（読めない）**: 「機能」から始めて 6 項目を順に展開し、「で、何が悪いのか」が 5 段落目に来る。読み手は 3 往復した。

**after（期待水準）**:

> 簡単にいうと —— **この 1 行だけ try/catch で囲み忘れている。**
>
> 同じファイルの他の 2 箇所（:105, :164）は囲んであり、失敗時は固定文言 `"Service temporarily unavailable"` を返す。ここだけ囲んでいないため、`verifyReportDlJwt` 内部の SSM 取得が失敗すると `DependencyUnavailableError` が `withErrorHandling` の AppError 分岐に落ち、**エラーの生 message（SSM パス文字列）がそのままレスポンス body に出る**。
>
> **前提**: このエンドポイントは `authorization = NONE`・API キーなし・WAF なしの**公開経路**（report-dl.tf:496-500）。Origin 検証は CSRF 対策で認証ではない（curl で `Origin` を偽装すれば通る）。署名検証前に SSM を読むため、正しい JWT も不要。
>
> **直し方**: 他の 2 箇所と同じ形にする。
> ```ts
> let verifyResult;
> try { verifyResult = await verifyReportDlJwt(token); }
> catch { return serviceUnavailable(corsHeaders, requestId); }
> ```
>
> **影響**: 漏れるのは SSM パス文字列のみ（鍵・トークンは漏れない）。かつ SSM が壊れている瞬間にしか出ない。**MEDIUM・マージブロッカーではない。**

## scope 外

- コードの自動修正・commit・push。
- review の submit、承認/マージ、CI 組込。
- 網羅的な観点別ゲートレビュー（それは `isolated-code-review`＝フルを使う）。
