# light-review

**認知負荷を下げた PR レビュー**プラグイン。finding のリストを吐くゲート（[`isolated-review`](../isolated-review)＝フル）とは役割が別物で、TAKT も使いません。

## 収録 skill

| skill | 説明 |
|---|---|
| `light-code-review` | 指摘は逆ピラミッド（場所 1 行 → 結論 1 文 → 最小根拠 → 直し方 → 影響 → 処分）で書き、重要度を左右する前提を指摘の中に埋め込む。処分まで書いて 1 件完成。OK だった箇所は理由を厚く残す。コードスメル中心・薄い指示。 |

## 何のためか

素の finding リストは「問題」しか言わず、読む人に前提が無い。人も LLM も「そもそもこのコードは何？作者は何をしたかった？あるべき姿は？」を毎回再構築させられ、その再構築コストが本当の負担になります。

削るのは指摘の数でも精度でもなく、**1 指摘を理解するのに必要な読解量**です。前提は **PR の意図から滝で下ろす**:

```text
このPRは何のため
  → 指摘箇所はその中のどの部分か
  → 実装者はどういう意図で
  → でも実際はこうなってて
  → あるべき姿との乖離
  → 放置の影響
```

ただし**書式は指摘と OK で非対称**にします。この滝を見出しごとフル展開するのは「確認して問題なかった箇所」だけ。指摘側は逆ピラミッドで、結論を冒頭に置き、前提は結論を支える最小限だけ後置します（実運用で、同じ内容でも書式が違うだけで読めなくなることが実測されたため）。

```text
`path:line`（`シンボル`） — 何をするコードか   ← 方角。省略しない
  → 簡単にいうと —— <核心 1 文>
  → 最小の根拠（file:line）
  → 前提（到達経路・消費者・監視の有無 …重要度に効くもの）
  → 直し方（差分レベルのコード）
  → 影響
  → 処分（直す / issue / 記録のみ / 要確認）
```

「軽い」＝**読む人の認知負荷が軽い**であって、計算量や観点数を減らすことではありません。目的は、PR を見て人に新しい学びが残ること（OK を置いた理由が残ること）、前提不足による判断コストを軽減すること、そして **PR に pending review（draft）で乗せて運用**することです。

### 読解量を削る過程で落としてはいけない 2 つ

- **方角** ——「どこの・何をするコードの話か」。6 項目の「機能」見出しを禁止したときに、指摘から方角ごと消えた。見出しではなく**場所 1 行**で持たせる（長さは戻らない）
- **処分** ——「誰が・いつ・どこで片付けるか」。処分の無い指摘は、読み手に**トリアージという第 2 の作業**を発生させる。書いた人が書かなければ、読んだ人が書くことになる

## 運用上の決め事

- **処分（直す / issue / 記録のみ / 要確認）まで書いて 1 件完成**。severity ラベルは処分の代わりにならない
- **既に人が処分を決めた件を再提起しない**。レビュー前に既存コメント（bot 含む）を突合し、決着済みは畳む
- **「本 PR 由来でない × 動作影響ゼロ × 直さない」が揃った指摘は本文に出さない**（末尾に 1 行で畳む）。畳むか記録に残すかは「3 ヶ月後に同じ疑問を持つ人がいるか」で決める
- **アンカーは「本文の主対象ファイル」に置く**。diff 上で近いからという理由で別ファイルに置かない
- **severity は「マージを止めるか」の一軸で言い切る**（ラベルだけ置かない）
- **未検証の主張を検証済みと同じ口調で書かない**（`要確認` 節と確定方法を添える）
- **スコープは本 PR が追加した行のみ**。base 追いつき待ちで diff に見えている他 PR の変更は件数にも severity にも含めない
- **抽象化・共通化を求める前に `.claude/rules/` の発動条件を確認する**（閾値未満で共通化を求めると指摘側が規約違反になる）
- **verdict は出さない**。pending review を置くまでで止め、submit は人間が行う

## 前提

- `gh` CLI（PR を対象にする場合）。private repo では MCP GitHub が 404 になるため `gh api` を使います。TAKT は不要です。

## 使い方

Claude Code で:

```text
/light-code-review        # 対象PRを確認 → PR意図の取り込み → スコープ確定 → コードスメル中心の説明レビューを生成
```

read-only。コードは変更せず、まずはレビュー文を生成するだけです（自動投稿はしません）。投稿を望んだ場合は `gh api` でインライン付き pending review を置き、submit はしません。

## フル（isolated-review）との使い分け

| | light-review | isolated-review（フル） |
|---|---|---|
| 役割 | 前提を配る説明役 | 観点別の敵対的ゲート |
| 観点 | コードスメル中心（薄い指示） | correctness / regression / tests / security / overall |
| 出力 | 逆ピラミッドの指摘＋厚い OK 理由 | severity 付き finding リスト |
| 分離 | なし（親セッションで実行） | 独立セッション並列＋統合セッション |
| 依存 | `gh` | TAKT |
