# draft-review-loop

codex が作った **draft PR** を、人間がレビューできる状態まで運ぶ**オーケストレーション**プラグイン。

レビューの中身は書きません。中身は [`light-review`](../light-review) / [`isolated-review`](../isolated-review) に委譲し、このプラグインが持つのは**順序・反復・打ち切り・出口**です。

## 収録 skill

| skill | 説明 |
|---|---|
| `codex-draft-review` | プロセス準拠チェック → 自己レビューと対応の反復 → 検証 → codex レビュー依頼と全コメントの返信・クローズ → 受入要件の最終確認 → draft 解除。1 PR 分だけ実行する。 |

## 何のためか

codex に draft を量産させる運用では、ボトルネックが「レビューの質」ではなく**「レビューを最後まで回しきること」**に移ります。実際に落ちるのは次の 3 つで、いずれも観点を増やしても直りません。

- **終了条件が無い。**「指摘がなくなるまで繰り返す」は、上限も抜け方も書かれていないと、永久に回るか勝手に打ち切られるかのどちらかになる
- **最後の修正が未検証のまま出口を通る。** レビュー対応でコードが変わったのに、検証はその前で終わっている
- **受入要件を出口で初めて見る。** 入口で見ていないと、全工程をやり直す最も高い手戻りになる

そこでこのループは、**受入要件を入口で厚く・出口で確認**し、**コードが変わる各ループの直後に検証を置き**、**すべての反復に上限とエスカレーション先**を持たせます。

## ループの形

```text
 1. draft PR を 1 件選ぶ（0 件なら終了）
 2. プロセス準拠チェック（openspec-workflow / issue 紐づけ）
 3. レビュー（issue の受入要件 → request.md → delta spec の順に重い）
 4. 指摘に対応し、commit / push（自分のレビューは記録不要）
 5. 3〜4 を反復 ── 新規 0 件で次へ／5 周超でエスカレーション
 6. 検証（build / typecheck / lint / test）── 落ちたら 4 へ
 7. codex にレビューを依頼し、完了まで待機
 8. レビュー対応 → push。対応済み / wontfix いずれも返信のうえクローズ
 9. 7〜8 を反復 ── 新規なし かつ 未クローズ 0 件で次へ／5 周超でエスカレーション
10. 検証を再確認 ── 落ちたら 8 へ
11. issue の受入要件を最終確認 ── 満たさなければ 4 へ
12. draft 解除・reviewer アサイン
```

**手順 6 と 10 は同じ検証です。** 10 を省くと、手順 8 の修正が未検証のまま draft 解除されます。

## 運用上の決め事

- **1 呼び出し = 1 PR。** 「次の PR を拾い直す」周回は持たない。連続処理は `/loop /codex-draft-review` で外から回す
- **打ち切れないループを書かない。** 反復には「抜ける条件」「上限」「上限に達したときの行き先」を必ず持たせる
- **受入要件のソースは issue が頂点。** `request.md` / delta spec はその実装計画であって受入要件そのものではない
- **自分のレビューは記録に残さず対応だけする。** 往復記録が要るのは codex（＝他者）のレビューだけ
- **codex のコメントは、対応したものも wontfix も返信してからクローズする。** 無言のクローズは「読んでいない」と区別がつかない
- **直したら push してから次へ進む。** push していない修正は、codex には存在しない。「直したのに同じ指摘が返る」の典型的な原因
- **反復回数はファイルに書く。** セッション内変数だと compact で消え、エスカレーション判定が壊れる。`git rev-parse --git-dir` 配下の `draft-review-loop.json` に置く（コミットされず PR にも出ない）
- **同じ指摘が 2 回来たら周回を続けない。** 収束しないループを上限まで回すのは時間の無駄
- **draft 解除は最後。** 解除は「人間に渡す」意思表示であり、途中の状態を渡さない
- **マージはしない。** verdict は人間が決める

## 前提

- `gh` CLI。private repo では MCP GitHub が 404 になるため `gh api` を使います
- 対象リポジトリが **openspec-workflow を採用していること**。採用していないリポジトリでは手順 2・3 の根拠が無いため対象外です（`light-code-review` を単発で使ってください）
- 修正は worktree 側で行います。可能なら `request-fixup`（openspec-workflow）に委譲します

## 使い方

```text
/codex-draft-review                  # draft PR を 1 件、人レビュー待ちまで運ぶ
/loop /codex-draft-review            # draft が尽きるまで連続処理（間隔省略で自己ペーシング）
```

手順 7 の待機がセッションを長く占有する場合は、そこで中断して `/loop` の次の tick に回せます（state ファイルがあるため再開できます）。

## 他プラグインとの関係

| | draft-review-loop | light-review | isolated-review |
|---|---|---|---|
| 役割 | 回し方（運用ループ） | レビューのやり方（説明役） | レビューのやり方（敵対的ゲート） |
| 粒度 | PR 1 件の全工程 | 1 回のレビュー | 1 回のレビュー |
| コード変更 | する（対応まで） | しない | しない |
| 依存 | `gh` / openspec-workflow | `gh` | TAKT |
