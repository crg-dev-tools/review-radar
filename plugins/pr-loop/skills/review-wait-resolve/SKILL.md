# review-wait-resolve

**人待ちで止まっている PR** を 1 件選び、**止まっている理由に応じた一手**を打つ skill。

`merge-ready-sweep` が「判断が済んだもの」を外すのに対し、こちらは**判断が始まっていない／終わっていないもの**を動かす。

## これは何のためか（設計の芯）

`codex-draft-review` の出口も `bot-pr-resolve` の出口 B も「人に渡す」である。**渡した先には受け皿が無い。** 上流のループを速くするほど、ここに積み上がる。

積み上がった PR で実際に起きるのは次の 3 つで、いずれも**催促を増やしても直らない**。

- **止まっている理由が違うのに、見た目が同じ。** reviewer が居ないのと、居るが見ていないのと、変更要求のまま作者が止まっているのは、一覧では全部「open のまま」に見える。**打つ手が違うのに区別されない。**
- **催促は繰り返すと効かなくなる。** 同じ PR に 3 回目のコメントが付く頃には、誰も読まない。**1 回しか効かない手を、無計画に使い切らない。**
- **腐った PR が列を詰まらせる。** conflict と CI 落ちを抱えて数週間経った PR は、レビューしても意味がない。**動かすのではなく畳む判断が要る。**

だからこの skill は、**止まっている理由で 5 つに分類**し、**理由ごとに違う一手**を打ち、**催促は 1 PR につき 1 回**に制限する。

## 原則

- **分類してから動く。** 一手を打つ前に、なぜ止まっているかを特定する。特定できないなら人に渡す。
- **催促は 1 回まで。** 2 回目を打つ前に、**打つ相手か手を変える**（reviewer を替える / 作者に戻す / 人に判断を渡す）。
- **approve 済みには触らない。** それは `merge-ready-sweep` の担当。ここで二重に動かさない。
- **外部に通知しない。** 動かすのは PR の上（コメント・アサイン・ラベル）だけ。**Slack やメールに出すかは人が決める。**
- **腐敗は畳む判断として扱う。** 直すかどうかではなく、**このまま進める価値があるか**を人に聞く。
- **1 呼び出し = 1 PR。** ただし分類のために一覧は全件見る。

## 前提

- `gh` CLI（`gh auth status`）。**private repo では MCP GitHub が 404 になるので `gh api` を使う。**

## 状態の持ち方

`git rev-parse --git-dir` 直下に `pr-nudge.json` を置く。**催促した記録は PR を跨いで必要**（1 回制限のため）で、セッション内変数では消える。

```json
{ "nudged": { "142": { "at": "2026-08-19T02:00:00Z", "kind": "review-not-started" } } }
```

- マージ / close された PR の記録は消してよい。

## 手順

### 1. 止まっている PR を一覧して 1 件選ぶ

```bash
gh pr list --state open --json number,title,isDraft,author,createdAt,updatedAt,\
reviewDecision,reviewRequests,assignees,labels,mergeable \
  --jq '[.[] | select(.isDraft == false and .reviewDecision != "APPROVED")] | sort_by(.updatedAt)'
```

- **draft は対象外**（まだ人待ちではない）。**approve 済みも対象外**（`merge-ready-sweep` の担当）。
- **0 件ならその旨だけ報告して終了する。**
- 選ぶのは **`updatedAt` の古い順に 1 件**。ただし手順 2 で「まだ待つべき」と分類されたものは飛ばす。

### 2. 止まっている理由で分類する（5 つ）

**滞留の起点は `updatedAt` ではなく、その状態になった時刻で測る。** 自動コメントが付くだけで `updatedAt` は動くので、これを待ち時間の根拠にしない。

| # | 理由 | 見分け方 | 一手（手順 3） |
|---|---|---|---|
| 1 | **reviewer が居ない** | `reviewRequests` も `assignees` も空 | 3-A アサインする |
| 2 | **レビュー未着手** | reviewer は居るが review が 1 件も無く、**依頼から 2 営業日以上** | 3-B 1 回だけ突く |
| 3 | **変更要求のまま放置** | `reviewDecision == "CHANGES_REQUESTED"` で、**その後に作者の push が無く 1 週間以上** | 3-C 作者に返す |
| 4 | **再依頼されていない** | 変更要求の後に**作者の push はある**が、re-request review がされていない | 3-D 再レビューを依頼する |
| 5 | **腐敗** | conflict または必須 check が赤のまま **3 週間以上**、あるいは base から大きく離れた | 3-E 人に畳む判断を渡す |

- **どれにも当てはまらない（依頼から 1 日など、まだ待つべき）ものは触らない。** 待ち時間が足りない PR を突くのが、催促を効かなくする一番の原因。
- 複数該当するときは**番号の大きい方**を採る（腐敗が最優先）。

### 3. 一手を打つ

#### 3-A. reviewer が居ない → アサインする

```bash
gh api repos/{owner}/{repo}/pulls/<n>/files --jq '[.[].filename]'   # 触っているファイル
gh pr edit <n> --add-reviewer <handle>
```

- 選び方は **CODEOWNERS → そのファイルの直近のコミッタ**の順。どちらも決まらないなら**人に聞く**（勝手に誰かの仕事にしない）。
- **アサインしたら、そこで終わり。** 同じ tick で催促まで続けない。

#### 3-B. レビュー未着手 → 1 回だけ突く

```bash
gh pr comment <n> --body "..."
```

コメントに書くのは 3 点。**「見てください」だけ書かない。**

- **何の PR か**（1 文。タイトルの再掲ではなく、何が変わるか）
- **どれくらいで読めるか**（変更行数・ファイル数・レビュー観点が 1 つなら 1 つと書く）
- **止まっている期間**（「依頼から 4 日」）

state に `nudged` を記録する。**2 回目は打たない。** 次に同じ PR が該当したら、**reviewer を替えるか人に渡す**。

#### 3-C. 変更要求のまま放置 → 作者に返す

- 作者が bot / codex なら、**`codex-draft-review` に渡す**（あちらがレビュー対応のループを持っている）。
- 作者が worker（openspec-workflow の request）なら、**`worker-fleet-loop` が `/request-fixup` を投げる**担当。この skill は**ラベルと 1 行コメントで「作者待ち」だと明示するだけ**にする。
- 作者が人なら、**人に渡す**。他人の PR を勝手に直さない。

#### 3-D. 再依頼されていない → 再レビューを依頼する

```bash
gh api -X POST repos/{owner}/{repo}/pulls/<n>/requested_reviewers -f 'reviewers[]=<handle>'
```

- **これは催促に数えない。** 作者は対応済みで、**ボールがレビュアーに渡っていないだけ**の状態であり、突く相手が違う。
- 何を直したか（作者の最後のコミット 1〜2 行）をコメントに添える。**再レビューは「差分の差分」を見れば済むことが多い。**

#### 3-E. 腐敗 → 畳む判断を人に渡す

**直すかどうかではなく、このまま進める価値があるかを聞く。**

- 経過（何週間・conflict の有無・CI の状態）を 3 行で書く
- 選択肢を**具体的に 2 つ**出す（「base から作り直す」「close して issue に戻す」等）
- **勝手に close しない。** 作業を捨てる判断は人のもの。

### 4. state を書き、1 行で報告する

```text
#142 レビュー未着手（依頼から 4 日）→ 1 回目の催促｜次に該当したら reviewer 交代を提案
```

### 5. 終了

次の PR には進まない。連続処理は `/loop /review-wait-resolve` に任せる。

---

## エスカレーションの書式

- **どの PR か**（番号・分類・滞留期間）
- **なぜこの skill では動かせないか**（reviewer の候補が決まらない / 作者が人 / 腐敗）
- **人間に何を決めてほしいか**（1 つに絞る）

## scope 外

- **approve 済みの PR。** `merge-ready-sweep` の担当。
- **マージ。** この skill はマージしない。
- **他人の PR のコード修正。** 作者に返す。
- **外部への通知**（Slack / メール）。PR の上でだけ動く。
- **レビューそのもの。** `light-code-review` / `isolated-code-review` の責務。
